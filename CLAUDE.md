# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Контекст проекта для агента. Читать перед любыми изменениями кода.

## Состояние репозитория

**План пройден целиком: фазы 0–13.** Дальше — то, что в `IMPLEMENTATION_PLAN.md` вынесено
в «TODO: на подумать» и «Что осознанно не делаем».

Перед каждым релизом прогонять приёмку целиком, а не выборочно:

```bash
./gradlew test --tests '*AcceptanceTest*'   # четырнадцать пунктов чеклиста безопасности
```

Пропуск на сервер даёт погашенное приглашение, а не подпись: подпись говорит «это тот же
ключ», а не «его сюда звали». Owner-инвайт печатается в журнал при первом старте, один раз
и только пока нет владельца.

Что работает:

- **Личность устройства.** Seed в IndexedDB, обе пары ключей выводятся из него
  детерминированно, экспорт 24 словами, в `key.enc` и по QR, импорт всеми тремя способами.
- **Вход по подписи вызова.** Ключ сервера в `data/server.key`, отказ старта при открытых
  правах. Клиент проверяет подпись сервера и запоминает его отпечаток.
- **Комнаты.** Карта из `HMAC(room_id, pubkey)`, `wrapped_room_key` под X25519 каждого
  участника, эпохи ключа. Ссылка участника — `#<номер>`, ключ приезжает обёрткой.
- **Приглашения.** Токен делает клиент, серверу уходит только SHA-256; в ссылке
  `/join#<токен>.<эфемерный ключ>` едет эфемерный приватный ключ, а не ключ комнаты.
  Вход по номеру комнаты закрыт.
- **Владелец сервера.** `instance_owner`, наполняется погашением owner-инвайта
  (`invite` с `room_id IS NULL`). Без пропуска нельзя даже завести комнату.
- **Вложения.** Пропуск на загрузку выдаётся по сокету, тело едет `POST /api/file`
  заголовком `X-Upload-Token`. Ключ на каждый файл свой, `secretstream` чанками по 256 КБ;
  ключ, имя и MIME-тип лежат внутри сообщения. Скачивание открыто без входа: имя блоба
  и есть пропуск, а без ключа из сообщения там мусор.
- **Одноразовые записки.** Ключ у записки свой, не ключ комнаты. Страница `/once` отдельная
  от SPA: открывающий может быть посторонним, заводить ему личность устройства незачем.
  Сжигание — `POST /api/once` с токеном **в теле**; GET только показывает предупреждение,
  иначе превью-боты сожгли бы ссылку до человека.
- **Личные сообщения.** Рассылка на всю колоду: 52 слота по 80 байт, настоящих два —
  получателю и себе. Ключ переписки выводится из seed на пару «комната + эпоха», лежит
  в `dm_key`. Подпись отправителя внутри шифротекста, снаружи ни его, ни получателя нет.
  Файлов в личных нет: блоб один, и сервер видит, кто его качает.
- **Модерация.** Исключение: пометка в базе, ротация эпохи, разрыв сессий — именно в таком
  порядке. Карта остаётся занятой. Зачистка стирает содержимое комнаты, но не комнату.
- **Анти-абьюз.** Счётчики попыток в памяти (`RateLimiter`), один общий счётчик на все
  виды записи. Hashcash на создание комнаты и выпуск приглашения; `app.work.bits=0`
  выключает проверку целиком.
- **Упаковка.** Сборка воспроизводима (`preserveFileTimestamps = false`), `./gradlew
  releaseHashes` даёт сумму jar. Отпечаток бандла считается по всему, что уходит в браузер,
  и печатается при старте — по нему сверяют, тот ли код раздаётся.

Формат сообщения — конверт с версией: `{v: 1, t: 'text'|'file', …}`. **Не выпускать формат
без поля версии**: без него смена криптосхемы ломает всё отправленное, и миграцию некуда
зацепить.

Ed25519 на сервере — штатный из JDK (`java.security`, с 15-й версии), стороннего крипто
не тащили. Преобразование сырых 32 байт в точку кривой — только в `auth/Ed25519Keys`,
сверено с векторами RFC 8032.

Не проверено на живом устройстве: захват кадра камерой при сканировании QR. Остальная
цепочка переноса прогнана, цикл сканирования — на подставном потоке с холста.

Тестов на JS нет, npm не заводили: он против вендоринга без сборщика. Ассерты гоняются
в браузере страницами из `src/test/resources/browser/` — в jar они не попадают, но `bootRun`
раздаёт их по `/browser/` из `build/browser-tests/` (задача `stageBrowserTests` в
`build.gradle`). Открывать с того же origin обязательно: иначе `import` из `/js/` не
разрешится. Страницы, работающие с личностью, **стирают хранилище ключа на своём origin** —
на боевом домене не открывать. Существующие тесты:
- `identity-selftest.html` — генерация/экспорт/импорт ключей
- `export-selftest.html` — 24 слова по векторам BIP-39 и `key.enc`
- `transfer-selftest.html` — перенос по QR
- `attach-selftest.html` — шифрование/расшифровка файлов (хранилище ключа не трогает)
- `direct-selftest.html` — конверты личных сообщений (хранилище ключа не трогает)

Известный зазор: `ApplicationReadyEvent` срабатывает после открытия порта, поэтому
«чистит базу до раздачи трафика» выполняется не буквально. Наружу протухшее всё равно
не уходит — держит фильтр при чтении.

Репозиторий публичный, под AGPL-3.0. Отсюда два правила поверх остальных: **адрес живого
стенда, домен и любые данные развёртывания в репозиторий не попадают** — им место в конфиге

документы, не витрина.

Прежде чем писать код, свериться с планом: там фазы упорядочены так, чтобы рискованное
проверялось раньше дешёвого, и у каждой есть свой критерий «готово». Порядок не менять
без причины — инвайты и ротацию ключей поверх работающего скелета накручивать легко,
наоборот больно.

### Три грабли SQLite, на которые уже наступили

Все три молчат при неверной настройке — ничего не падает, просто не работает.
Проверяются тестом `DatabaseBootstrapTest`, не глазами.

1. **Неизвестный параметр JDBC-URL драйвер не отбрасывает, а оставляет в имени файла.**
   `auto_vacuum` он не знает — база создалась под именем `messenger.db?auto_vacuum=incremental`.
   В URL держать только то, что драйвер понимает: `journal_mode`, `busy_timeout`, `foreign_keys`.
2. **`PRAGMA auto_vacuum` не работает ни из миграции, ни из `connection-init-sql`.** В транзакции
   (а Flyway гонит миграцию в транзакции) SQLite его игнорирует, а после `journal_mode=WAL`
   файл базы уже инициализирован и смена режима требует `VACUUM`. Живёт в
   `config/DataSourceConfig` как `FlywayMigrationStrategy`, до миграций и однократно.
3. **Внешние ключи в SQLite выключены по умолчанию.** Без `foreign_keys=true` весь
   `ON DELETE CASCADE` в схеме — просто текст, и удаление комнаты оставит её сообщения жить.

`prototype.html` открывается в браузере как есть, без сборки, и служит источником правды
по интерфейсу: раскладка ленты, шторка отпечатка, счётчик колоды, вкладка личного.
Это макет на моках, не заготовка кода — крипто и сети в нём нет.

## Что это

Веб-мессенджер без нативного клиента. Открывается в браузере, работает по сквозному
шифрованию, вход по инвайт-ссылкам без почты и телефона, история самоудаляется по TTL.
Разворачивается self-hosted: один fat jar плюс каталог с данными.

## Модель угроз и что из неё следует

Сервер — транспорт и хранилище шифротекста. Он **не должен** иметь возможности прочитать
переписку даже при полном доступе к диску и памяти процесса.

Из этого следуют жёсткие правила, которые нельзя нарушать ни ради удобства, ни ради фич:

1. Открытый текст сообщений никогда не покидает браузер. На сервере — только blob.
2. Секреты (инвайт-токены, ключи комнат) передаются во **фрагменте URL**, после `#`.
   Фрагмент не уходит на сервер, не попадает в логи веб-сервера и в заголовок Referer.
   Любой код, который перекладывает секрет во фрагменте в query-параметр или путь, — баг.
3. На сервере хранятся только **хэши** токенов (SHA-256), никогда не сами токены.
4. Приватные ключи устройств живут в IndexedDB браузера и никуда не отправляются.
5. Не логировать: полные URL, содержимое сообщений, публичные ключи участников комнат.
   IP-адреса — только в объёме, который нужен rate-limiter'у, без записи на диск.

Self-hosted-модель снимает главный риск веб-E2E: бандл раздаёт тот же человек, который
администрирует сервер. Атака «сервер подсунул вредоносный JS» вырождается в самоатаку.
Релизы всё равно подписываются, хэш бандла публикуется — чтобы админ мог сверить, что
развернул именно то, что скачал.

## Стек и решения

| Область | Решение | Почему не альтернатива |
|---|---|---|
| Фреймворк | Spring Boot 3 | явный выбор пользователя |
| Транспорт | сырой `WebSocketHandler` | STOMP тянет брокерную семантику и `stompjs`; по проводу летят непрозрачные блобы, роутить нечего |
| Аутентификация | challenge-response на `HandshakeInterceptor` | Spring Security нечего дать при подписи ключом устройства, зато придётся отключать CSRF и form-login |
| Данные | Spring Data JDBC / `JdbcTemplate` | схема плоская, JPA-кэш и ленивая загрузка мешают |
| БД | SQLite, WAL, `busy_timeout=5000` | Redis нечего масштабировать горизонтально; бэкап = каталог `data/` целиком |
| Миграции | Flyway | апдейт бинарника не должен ломать существующую базу |
| Контейнер сервлетов | Undertow | экономнее Tomcat на большом числе простаивающих соединений |
| Фронтенд | SPA в `resources/static` | один артефакт, отдельный веб-сервер не нужен |
| Крипто на клиенте | libsodium.js | WebCrypto не даёт X25519 sealed box из коробки |
| TLS | Caddy впереди | автоматический Let's Encrypt, в Java не заводим |

Java 21, Gradle, стартеры `websocket` + `jdbc` + `undertow`, Tomcat исключить.
**Не подключать: Security, JPA, Actuator, Thymeleaf** — каждый из них тянет за собой
конфигурацию, которую потом придётся отключать. libsodium.js вендорить в `static/`,
не с CDN: бандл должен собираться и раздаваться целиком с того же сервера, иначе
публикация хэша релиза ничего не значит.

## Криптосхема

- У устройства две пары ключей: **Ed25519** для подписи (аутентификация) и **X25519**
  для шифрования (получение ключа комнаты). Генерятся в браузере при первом входе.
- У комнаты симметричный ключ `room_key` (XChaCha20-Poly1305). Он зашифрован отдельно
  под каждое устройство-участника и хранится на сервере как `wrapped_room_key`.
- **Во фрагменте инвайт-ссылки едет не `room_key`, а эфемерный приватный ключ инвайта**
  (`#<token>.<ephemeral_priv>`). Сам `room_key`, обёрнутый под эфемерный публичный, лежит
  на сервере в `invite.wrapped_key` и удаляется вместе с погашением инвайта. Иначе
  пересланная ссылка навсегда остаётся ключом от комнаты — даже исчерпанная, а превью-боты
  и архивы такие ссылки видят. Положить `room_key` прямо во фрагмент — баг, не упрощение.
- Новичок разворачивает `room_key` эфемерным ключом, тут же перешифровывает под свой X25519
  и отдаёт серверу обёртку в `member_key`. Дальше ключ приходит только так.
- Double Ratchet **не используется** — избыточен для круга из десятков людей.
  Forward secrecy обеспечивается ротацией `room_key` по эпохам (`key_epoch`).
- При удалении участника — обязательная ротация эпохи. Старую историю удалённый
  расшифровать сможет, новую нет. При TTL в пару дней это приемлемо.

## Файлы

Лимит — **20 МБ на файл**, жёсткий. Он выбран не по вкусу: именно на этой границе не нужны
Service Worker, потоковая расшифровка, возобновляемая загрузка и Range-запросы. Поднятие
лимита возвращает все четыре пункта сразу.

- Загрузка отдельным HTTP-эндпоинтом (`POST /api/file`, `application/octet-stream`),
  не по WebSocket — иначе большой файл забивает канал сообщений.
- Авторизация загрузки — короткоживущий upload-токен, выдаётся по сокету.
- Лимит проверяется **на сервере**, по `Content-Length` и по фактически прочитанным байтам.
  Клиентская проверка — только UX. Порог в байтах шифротекста (~21 МБ), не открытого текста.
- Блобы в `data/blobs/<id>`, метаданные в SQLite. BLOB'ы в базе раздувают файл и требуют
  долгого `VACUUM` после массовых удалений.
- **Случайный ключ на каждый файл.** Ключ, имя и MIME-тип живут внутри сообщения,
  зашифрованного `room_key`. В схеме БД их нет — имя файла это метаданные.
- Сервер видит только размер и время. Размер тоже утекает; паддинг до степени двойки —
  кандидат на будущее.
- **Удалять в порядке: блоб, затем строка в БД.** Обратный порядок оставляет вечный мусор
  на диске. При старте — скан на осиротевшие блобы (`FileService.removeOrphans`, зовёт его
  `SweeperJob.sweepOrphanBlobs` на `ApplicationReadyEvent`). Признак «загрузка ещё идёт» —
  невыданный токен, а не возраст файла: часы приложения и время на диске идут порознь.
- Антивирусная проверка при E2E невозможна в принципе. Написать это в UI, а не умалчивать.

Реализация в пакете `file/`:
- `FileController` — HTTP-эндпоинты загрузки/скачивания
- `FileService` — создание upload-токенов, валидация, квоты
- `BlobStore` — работа с `data/blobs/`, cleanup осиротевших
- `Upload` — короткоживущий токен авторизации загрузки
- `StoredFile` — метаданные файла (без ключа расшифровки)

## Имена участников: колода

Участник получает карту, а не выбранный ник. Имя выводится из ключа — `HMAC(room_id, pubkey)`
даёт позицию в колоде — и выбрать его нельзя, значит и подделать нельзя. В анонимной комнате
свободный ник это готовый вектор выдачи себя за другого.

Привязка к `room_id` обязательна: без неё один человек во всех комнатах одна и та же карта,
и участники разных комнат сопоставляют, что это одно лицо.

**Уникальность не правило, а свойство конструкции.** В колоде не бывает двух дам треф, поэтому
разрешение коллизий, счётчики и словарь форм прилагательного не нужны вовсе.

**Выбывшие карты не возвращаются в колоду.** Иначе «восьмёрка бубён» через неделю окажется
другим человеком, а её старые реплики останутся висеть в ленте выше. Отсюда потолок: **52
участника за всё время жизни комнаты**, а не одновременно. Когда колода кончилась, комната
больше никого не принимает — это её естественный конец, и он должен быть отдельным состоянием
с внятным текстом, а не ошибкой выдачи инвайта.

Масти рисуются монохромно, различаются формой. Красный не вводить: акцентный цвет
зарезервирован под необратимые действия.

**Карта и масть ничего не означают** — раздача случайна, ранг не иерархия, масть не роль.
Роль в ленте не показывается вообще: она нужна только в момент действия (выпуск инвайта,
исключение участника), и там её место, а не рядом с каждой репликой.

Карта это меньше шести бит, и назначает её сервер. **Якорь доверия — отпечаток и фраза сверки,
карта только подсказка памяти.** Помнить, что абстрактная карта цепляется за память хуже
персонажа, и подмену на ней замечают позже.

## Личные сообщения

Живут внутри комнаты — карта существует только здесь, отдельного списка контактов быть
не может, он связал бы личности между комнатами.

**Получатель скрыт от сервера рассылкой на всю колоду.** Текст шифруется случайным ключом
один раз, а ключ кладётся в 52 конверта по числу мест: в слоте получателя настоящий sealed box,
в остальных случайные байты той же длины. Вывод sealed box неотличим от случайного, поэтому
сервер не знает, кому адресовано. Клиент разворачивает только свой слот.

Жёсткие следствия, нарушение любого раскрывает получателя:
- слотов всегда ровно 52, включая места выбывших;
- все слоты одной длины;
- в схеме нет ни поля получателя, ни отправителя — подпись лежит **внутри** шифротекста.

Ключ переписки `pubkey_dm` свой на каждую эпоху комнаты. Иначе утечка долгоживущего ключа
раскрывает всю личную переписку задним числом: ротации ключа комнаты она не подчиняется.

Сроки — те же, что у обычных сообщений, потолок 5 суток. Отдельных правил не заводить.

Интерфейс — отдельная вкладка. В общей ленте личных сообщений нет, чтобы не путать личное
с общим.

**Файлы в личных сообщениях не поддерживаются.** Блоб один, и сервер видит, кто его качает —
текст получателя скрывает, а вложение выдаёт. Утечка известна, решения пока нет; поддерживать
файлы «с оговоркой» нельзя, это ровно тот случай, когда оговорку не прочитают.

Администратор не видит личную переписку и не может её модерировать. Отсюда настройка комнаты
«личные сообщения запрещены», решаемая при создании.

## Персистентность и TTL

Главное правило: хранится **абсолютный дедлайн** `expires_at` (UTC millis), а не остаток
TTL. Тогда рестарт и простой сервера вообще не участвуют в жизни сообщения.

Срок задаёт отправитель при отправке. Границы: **потолок 5 суток, по умолчанию 48 часов.**

Потолок держится низким сознательно: исключённый участник сохраняет ключ старых эпох и
уносит с собой читаемую историю за этот срок — перешифровать её невозможно. На пяти сутках
исключение остаётся осмысленным, на полутора месяцах превратилось бы в формальность.

**Срок приходит от клиента, поэтому сервер обязан его зажимать** в допустимый диапазон.
Сам факт, что одно сообщение живёт пять минут, а другое пять дней, сервер видит открытым —
это метаданные, скрыть их нельзя, надо просто знать.

Угасание в интерфейсе считать в **абсолютном времени**, а не в доле от срока: последние
десять минут независимо от того, был срок час или пять суток. Иначе долгоживущее сообщение
проведёт почти двое суток полупрозрачным и будет выглядеть как поломка.

Квота на комнату и на инстанс всё равно нужна — при 52 участниках и файлах по 20 МБ пять
суток накопления дают заметный объём, — но при таком потолке TTL остаётся основным
механизмом уборки, а квота страховкой.

Что обязано пережить рестарт и не генерироваться заново:
- ключевая пара сервера (для подписи challenge) — `data/server.key`, права 600;
- комнаты, участники, `wrapped_room_key`, эпохи;
- инвайты (хэш + TTL + счётчик использований);
- шифротексты сообщений — доживают до своего `expires_at`;
- схема БД — только через Flyway.

Owner-инвайт печатается в stdout **только если в базе нет ни одного владельца**.
Никакой формы регистрации админа, никакого повторного онбординга после рестарта.

Sweeper: `@Scheduled(fixedDelay = 30_000)` плюс прогон на `ApplicationReadyEvent`, чтобы
после долгого простоя база чистилась сразу. При чтении всё равно фильтровать
`WHERE expires_at > ?` — окно между тиками не должно отдавать протухшее.

В памяти живёт только `Map<roomId, Set<WebSocketSession>>`. Переживать рестарт ему не
нужно: клиент переподключается, подписывает challenge и запрашивает `since=<last_seen_id>`.

## Как проверять изменения

Перед тем как считать задачу готовой:
- секрет во фрагменте не появился в логах Undertow и в `access.log` Caddy;
- переоткрытие вкладки и разрыв связи не теряют сессию и не требуют нового инвайта;
- рестарт сервера не сбрасывает комнаты и не воскрешает протухшие сообщения;
- у одноразовой ссылки второй запрос и запрос протухшей дают **одинаковый** ответ —
  различать их наружу нельзя;
- присланный клиентом срок жизни зажат сервером, а не принят на веру;
- у фазы, которую делали, пройден её собственный критерий «готово» из
  `IMPLEMENTATION_PLAN.md` — они там сформулированы как проверки, а не как ощущения.

Полный приёмочный чеклист по безопасности — `AcceptanceTest`, четырнадцать пунктов
с номерами из фазы 13 плана. Прогонять перед релизом целиком, а не выборочно: половина
пунктов ловит ровно те ошибки, которые снаружи выглядят исправной работой.

Две вещи в приёмке проверяются живым прогоном, а не тестом: строки самого старта
(отпечаток бандла, owner-инвайт) и журнал за длительную работу.

## Стиль работы с проектом

- **Сверяться с планом перед кодом.** Фазы упорядочены так, чтобы рискованное проверялось
  раньше дешёвого. Порядок не менять без причины.
- **Критерии «готово» фаз — это проверки, не ощущения.** Они сформулированы как действия,
  которые надо прогнать, а не как «убедиться что всё работает».
- **Тесты пишутся на Java, не на JS.** npm не заводили, libsodium вендорится без сборщика.
  Браузерные тесты — только для того, что невозможно проверить иначе (QR, камера, rAF).
- **Не логировать секреты.** Полные URL, ключи, токены, публичные ключи участников —
  всё это не должно попадать в stdout/stderr. IP-адреса — только для rate-limiter'а.
- **Инварианты из модели угроз нельзя нарушать.** Открытый текст не покидает браузер,
  секреты только во фрагменте URL, сервер хранит только хэши токенов. Нарушение любого
  из правил раздела «Модель угроз» — это баг уровня блокера, не техдолг.
