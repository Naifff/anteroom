# План реализации

Порядок фаз выбран так, чтобы рискованное проверялось раньше дешёвого. Инвайты, роли и
ротацию ключей поверх работающего скелета накручивать легко, наоборот — больно.

---

## Фаза 0. Каркас — СДЕЛАНО

**Задачи**
- Gradle-проект, Spring Boot 3, Java 21. Стартеры: `websocket`, `jdbc`, `undertow`.
  Tomcat исключить. Не подключать: Security, JPA, Actuator, Thymeleaf.
- `sqlite-jdbc`, `flyway-core`, `libsodium.js` в статику (вендорить, не с CDN).
- Проперти `app.data-dir` (по умолчанию `./data`), каталог создаётся при старте.
- `bootJar` собирает один артефакт, SPA лежит внутри.

```yaml
app:
  data-dir: ./data
spring:
  datasource:
    url: jdbc:sqlite:${app.data-dir:./data}/messenger.db?journal_mode=WAL&busy_timeout=5000&foreign_keys=true
    hikari:
      maximum-pool-size: 4        # SQLite однопоточен на запись, больший пул даёт SQLITE_BUSY
  flyway:
    enabled: true
  lifecycle:
    timeout-per-shutdown-phase: 20s
server:
  shutdown: graceful
```

**Три грабли SQLite, все молчаливые** — при неверной настройке ничего не падает, просто
не работает. Закрыты тестом `DatabaseBootstrapTest`, проверять их глазами в логе нельзя.

1. **Неизвестный параметр JDBC-URL драйвер не отбрасывает, а оставляет в имени файла.**
   `auto_vacuum` он не знает — база создаётся под именем `messenger.db?auto_vacuum=incremental`.
   В URL держать только понятное драйверу: `journal_mode`, `busy_timeout`, `foreign_keys`.
2. **`PRAGMA auto_vacuum` не работает ни из миграции, ни из `connection-init-sql` пула.**
   Внутри транзакции (а Flyway гонит миграцию в транзакции) SQLite его игнорирует, а после
   `journal_mode=WAL` файл базы уже инициализирован, и смена режима требует `VACUUM`.
   Живёт в `config/DataSourceConfig` как `FlywayMigrationStrategy`: до миграций, однократно,
   с проверкой применённого режима.
3. **`foreign_keys` в SQLite выключены по умолчанию** — без флага весь `ON DELETE CASCADE`
   в схеме просто текст.

**Каталог данных создаётся раньше бинов**, слушателем на `ApplicationEnvironmentPreparedEvent`
(`config/DataDirectoryInitializer`, регистрация через `META-INF/spring.factories`): SQLite
открывает файл при инициализации пула, обычный `@Bean` до этого не успевает.

**libsodium** — сборка **sumo** (`libsodium-sumo` + `libsodium-wrappers-sumo`), два тега
`<script>` в этом порядке без сборщика: первый кладёт `window.libsodium`, второй `window.sodium`.
Обычная сборка не подходит — в ней нет `crypto_pwhash` (Argon2id для `key.enc`, фаза 3).
Версии и хэши — `static/vendor/PROVENANCE.md`.

**Готово когда** `java -jar app.jar` поднимается с пустого каталога, создаёт `data/`,
прогоняет миграции и отдаёт статику.

## Фаза 1. Walking skeleton — СДЕЛАНО

Самая важная фаза — проверяет три гипотезы, на которых держится вся схема.

Скелет шифрует по-настоящему, ключом из фрагмента (`crypto_aead_xchacha20poly1305_ietf`,
nonce впереди шифротекста): инвариант «открытый текст не покидает браузер» должен
выполняться с первой строки кода, а не появиться в фазе 5.

Протокол кадров, как он вышел: клиент шлёт `{"ciphertext":"<base64>"}` либо
`{"since":<id>}`, сервер отвечает `{"id","sender","ciphertext"}`. Отправитель получает
своё сообщение обратно, а не рисует его сразу: id приходит от сервера, и без этого
догрузка после реконнекта показала бы его второй раз.

**Известный зазор.** `ApplicationReadyEvent` срабатывает уже после того, как порт открыт,
поэтому «чистит базу до раздачи трафика» выполняется не буквально. Протухшее наружу всё
равно не уходит — его не пускает фильтр при чтении. Учесть в фазе 7.

**Задачи**
- Одна захардкоженная комната, `TextWebSocketHandler`, эхо всем участникам.
- `SessionRegistry` — `ConcurrentHashMap<String, Set<WebSocketSession>>`, потокобезопасное
  добавление и снятие сессий, снятие при `afterConnectionClosed` и при ошибке.
- Сообщения в SQLite с `expires_at = now + 60_000`, sweeper раз в 10 секунд.
- Клиент: две вкладки, обмен строками, ключ комнаты берётся из `location.hash`.

**Проверить руками**
1. Ключ во фрагменте не появился в логах Undertow и в Referer при переходе по внешней ссылке.
2. Реконнект вкладки не теряет сессию и не дублирует её в реестре.
3. Сообщение недоступно ровно через минуту — благодаря фильтру при чтении, а не потому что
   sweeper успел. Хвост до следующего тика нормален, выдача протухшего — нет.
4. Остановка сервера на две минуты и запуск: старые сообщения не воскресли, комната цела.

**Готово когда** все четыре пункта проходят. До этого дальше не идти.

## Фаза 2. Схема БД — СДЕЛАНО В ФАЗЕ 0

Перенесена вперёд: без единого файла миграции Flyway в фазе 0 нечего прогонять, а фазе 1
и так нужна таблица `message`.

`V1__init.sql`. Режим уборки (`auto_vacuum = INCREMENTAL`) **первой строкой не задаётся** —
из миграции этот PRAGMA не работает, см. грабли в фазе 0. Поменять режим потом можно только
полным `VACUUM` всей базы.

```sql
CREATE TABLE room (
  id            TEXT PRIMARY KEY,
  key_epoch     INTEGER NOT NULL DEFAULT 1,
  default_ttl   INTEGER NOT NULL DEFAULT 172800,   -- 48 ч
  max_ttl       INTEGER NOT NULL DEFAULT 432000,   -- 5 суток, потолок
  seats_taken   INTEGER NOT NULL DEFAULT 0,        -- карт роздано; 52 = колода кончилась
  created_at    INTEGER NOT NULL
);

CREATE TABLE device (
  pubkey_sign   TEXT PRIMARY KEY,      -- Ed25519, base64url
  pubkey_box    TEXT NOT NULL,         -- X25519
  created_at    INTEGER NOT NULL,
  label         TEXT
);

-- участие: одна строка на человека в комнате, эпохи её НЕ размножают
CREATE TABLE member (
  room_id       TEXT NOT NULL REFERENCES room(id) ON DELETE CASCADE,
  pubkey_sign   TEXT NOT NULL REFERENCES device(pubkey_sign),
  role          TEXT NOT NULL,         -- owner | admin | member; в ленте не показывается
  card          INTEGER NOT NULL,      -- 0..51; выбывшая карта в колоду не возвращается
  invited_by    TEXT,                  -- для каскадного отзыва
  joined_at     INTEGER NOT NULL,
  left_at       INTEGER,               -- при выходе строка остаётся, карта не освобождается
  PRIMARY KEY (room_id, pubkey_sign)
);
CREATE UNIQUE INDEX idx_member_card ON member(room_id, card);

-- обёртки ключа комнаты: по строке на участника и эпоху
CREATE TABLE member_key (
  room_id          TEXT NOT NULL REFERENCES room(id) ON DELETE CASCADE,
  pubkey_sign      TEXT NOT NULL,
  epoch            INTEGER NOT NULL,
  wrapped_room_key BLOB NOT NULL,
  PRIMARY KEY (room_id, pubkey_sign, epoch)
);

CREATE TABLE invite (
  token_hash    TEXT PRIMARY KEY,      -- SHA-256 от токена
  room_id       TEXT REFERENCES room(id) ON DELETE CASCADE,
  role          TEXT NOT NULL,
  created_by    TEXT,
  wrapped_key   BLOB NOT NULL,         -- room_key под эфемерным ключом инвайта
  expires_at    INTEGER NOT NULL,
  uses_left     INTEGER NOT NULL
);

CREATE TABLE message (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  room_id       TEXT NOT NULL REFERENCES room(id) ON DELETE CASCADE,
  sender        TEXT NOT NULL,
  epoch         INTEGER NOT NULL,
  ciphertext    BLOB NOT NULL,
  created_at    INTEGER NOT NULL,
  expires_at    INTEGER NOT NULL
);

CREATE TABLE onetime (
  token_hash    TEXT PRIMARY KEY,
  room_id       TEXT NOT NULL REFERENCES room(id) ON DELETE CASCADE,  -- иначе wipe комнаты их не заденет
  ciphertext    BLOB NOT NULL,
  expires_at    INTEGER NOT NULL
);

CREATE INDEX idx_message_room_id  ON message(room_id, id);
CREATE INDEX idx_message_expires  ON message(expires_at);
CREATE INDEX idx_invite_expires   ON invite(expires_at);
CREATE INDEX idx_onetime_expires  ON onetime(expires_at);
```

Индекс `(room_id, id)` — под догрузку `since`. Индексы по `expires_at` — под sweeper,
без них он деградирует на десятках тысяч строк.

## Фаза 3. Идентичность на клиенте — СДЕЛАНО

Seed и обе пары, IndexedDB, 24 слова, `key.enc`, перенос по QR, экраны экспорта и импорта.

**Непроверенным остался только захват кадра камерой.** Всё остальное в цепочке переноса
прогнано: QR рисуется, читается обратно тем же `jsQR`, распаковывается своим кодом и не
распаковывается чужим. Цикл сканирования проверен подставным потоком с холста вместо
камеры — на реальном устройстве надо пройти путь руками.

**Шесть цифр — это меньше двадцати бит.** Схему держат две вещи разом: Argon2id на каждую
попытку и две минуты жизни кода. У снявшего экран через плечо есть и то, и другое навсегда,
поэтому срок здесь не украшение, а половина защиты — показывать QR дольше нельзя.
Срок лежит в переносе открытым (иначе получатель не поймёт, что опоздал) и потому входит
в связанные данные AEAD: правка в шестнадцатеричном редакторе ломает расшифровку.

`requestAnimationFrame` в скрытой вкладке не тикает, и сканирование встаёт. Для камеры
это нормально — на неё смотрят, — но помнить стоит.

**Под-seed для X25519.** Формула `BLAKE2b(seed, "box")` читается как (ключ, сообщение):
ключом идёт сам seed, сообщением домен `box`. Наоборот не выйдет — ключ BLAKE2b короче
16 байт libsodium не принимает, а «box» это три байта.

**Argon2id взят MODERATE — это 256 МБ памяти и около секунды на десктопе.** На мобильных
надо проверить руками: если WASM не получит столько, экспорт в файл отвалится. Параметры
лежат внутри `key.enc`, поэтому понизить их для новых файлов можно, не ломая старые.

**Тестов на JS нет и npm не заводили** — он против вендоринга без сборщика. Ассерты гоняются
в браузере страницами из `src/test/resources/browser/`, в jar они не попадают. 25 проверок,
слова сверяются с восемью официальными векторами BIP-39, а не с пониманием спецификации.
Запуск: поднять статику и открыть `identity-selftest.html` и `export-selftest.html`.
Страница идентичности **стирает хранилище ключа на своём origin**.

Экран назван «Ваш ключ», а не «Ваша карта»: карт до фазы 5 не существует.

**Задачи**
- Один seed на 32 байта — источник обеих пар. Ed25519 через `crypto_sign_seed_keypair`,
  X25519 через `crypto_box_seed_keypair` от производного под-seed (`BLAKE2b(seed, "box")`).
  Детерминированность обязательна: от неё зависит, что восстановленное устройство получит ту же
  карту и развернёт старые `wrapped_room_key`.
- Хранение: IndexedDB, привязка к домену. На iOS предложить установку на домашний экран —
  иначе Safari чистит хранилище примерно через неделю простоя и аккаунт исчезает сам.
- Три способа экспорта, все кодируют один и тот же seed:
  - 24 слова BIP-39, показ по явному нажатию с автоскрытием через 15 секунд;
  - файл `key.enc` под парольной фразой (Argon2id);
  - QR — только для переноса на устройство.
- Перенос на устройство: QR содержит seed, **зашифрованный шестизначным кодом**, код
  показывается отдельно и передаётся голосом. Без этого достаточно снять экран через плечо.
  QR живёт две минуты.
- Импорт: слова, файл с фразой или сканирование QR.

**Готово когда** ключи переживают перезагрузку браузера, импорт seed на другом устройстве
даёт те же публичные ключи и ту же карту, а обе копии работают одновременно.

## Фаза 4. Аутентификация — СДЕЛАНО, КРОМЕ ЗАКРЫТИЯ РЕГИСТРАЦИИ

Challenge-response, без Spring Security.

**Ed25519 взят из JDK**, стороннего крипто на сервер не тащили: он в `java.security`
с 15-й версии. Ключи ходят по проводу сырыми 32 байтами, как их отдаёт libsodium, и всё
преобразование в точку кривой лежит в `auth/Ed25519Keys` — байты little-endian, а старший
бит последнего это знак x, а не часть числа. Сверено с векторами RFC 8032.

**Вызов и подпись едут параметрами запроса.** Секрета в них нет: nonce одноразовый и
публичный, подпись под ним тоже. Caddy всё равно пишет access.log без query-строк.

**Гашение до проверки подписи, а не после.** `remove` атомарен, и два одновременных запроса
с одной парой не пройдут оба. Проверить, а потом удалить — готовое окно для повтора.

**Клиент проверяет подпись сервера до того, как подпишет что-то своим ключом**, и запоминает
отпечаток сервера при первом входе. Смена отпечатка не блокирует вход — у самохостера это
чаще переустановка, чем подмена, — но пишется в статус: отличить одно от другого может
только человек. Отпечаток лежит в IndexedDB рядом с seed, а не в localStorage: одно
хранилище на всё состояние личности.

**Осталось от фазы:** «неизвестное устройство без действующего инвайта — отказ на апгрейде».
Инвайтов до фазы 6 нет, и жёсткая проверка сейчас не пустила бы никого, поэтому
`device/DeviceService` запоминает устройство при первом успешном входе. Личность настоящая
и подтверждена подписью, но пускают любую — **до фазы 6 наружу не выставлять**.

**Поток**
1. `GET /api/challenge` → сервер отдаёт nonce (32 байта) с коротким TTL, держит в памяти.
2. Клиент подписывает nonce приватным Ed25519.
3. WebSocket-апгрейд с nonce и подписью. `AuthHandshakeInterceptor` проверяет подпись,
   гасит nonce (одноразовость обязательна — иначе replay) и кладёт `pubkey_sign` в атрибуты сессии.
4. Неизвестное устройство без действующего инвайта — отказ на апгрейде.

**Задачи**
- `ServerKeyStore`: пара сервера читается из `data/server.key`, генерится только если файла нет.
  Права 600, при неверных правах — отказ старта с внятным сообщением.
- `ChallengeService`: выданные nonce с TTL 60 секунд, гашение при использовании.
  **Лимит на выдачу по IP и потолок числа живых nonce** — эндпоинт открыт всем, и без потолка
  он превращается в способ съесть память сервера дешёвыми запросами.

**Готово когда** replay использованного challenge отбивается, а подмена подписи не проходит.

## Фаза 5. Комнаты и ключи — СДЕЛАНО

Захардкоженная комната скелета убрана вместе с `SkeletonRoomBootstrap`.

**Протокол комнаты**, кадры с полем `op`: `hello` (свой X25519), `create`, `join`, `enter`,
`key`, `wrap`, `send`. Сервер отвечает `room`, `msg`, `key`, `error`. Членство проверяется
на каждом действии отдельно: проверить один раз на входе мало — между входом и отправкой
участника могли исключить.

**Отказ один и тот же** на «нет такой комнаты» и «вы не участник»: различать их снаружи
означало бы отдавать номера существующих комнат перебором.

**Состав рассылается при входе новичка.** Без этого сидящие видят у него отпечаток вместо
карты и неверный счётчик мест, пока не переоткроют вкладку.

**Ссылка**: `#<номер>.<ключ>` — приглашение, `#<номер>` — возврат в свою комнату, где ключ
приезжает обёрткой под свой X25519 и разворачивается локально. Обе формы проверены руками.

**Срок жизни сообщения теперь берётся из комнаты**, а не из константы скелета: раз комната
хранит `default_ttl`, игнорировать его — значит держать в схеме поле-обманку. Выбор срока
отправителем и зажим присланного — по-прежнему фаза 7.

**Проверено руками:** двое в комнате читают друг друга под своими картами, счётчик мест
обновляется у обоих; третья вкладка с тем же номером комнаты и подменённым ключом получает
блобы и не расшифровывает ни один; возврат по «#<номер>» без ключа поднимает ленту через
обёртку, без дублей.

**Задачи**
- `RoomService`: создание комнаты, `default_ttl` и `max_ttl` задаются при создании и меняются владельцем.
- Раздача карт: позиция из `HMAC(room_id, pubkey)`, при занятой — следующая свободная.
  Выбывшие карты не освобождаются. При `seats_taken = 52` комната переходит в состояние
  «колода кончилась» и больше не принимает никого — это конец жизни комнаты, не ошибка.
- Клиент генерит `room_key`, оборачивает под X25519 каждого участника (sealed box),
  отправляет серверу только обёртки.
- При входе устройство получает свой `wrapped_room_key` для текущей эпохи и разворачивает локально.
- `KeyEpochService`: инкремент эпохи, перевыпуск обёрток для оставшихся участников.

**Готово когда** два устройства в одной комнате читают друг друга, а третье, не состоящее
в ней, получает от сервера только нерасшифровываемые блобы.

## Фаза 6. Инвайты — СДЕЛАНО

**Токен генерирует клиент, а не сервер.** Отступление от плана, и вот почему: сервер при
выпуске получает только SHA-256, то есть сам токен не проходит через него вовсе. При
погашении токен приходит целиком — иначе хранение хэша теряет смысл, ведь предъявившему
хэш открывать комнату нельзя, а прочитать базу проще, чем перехватить переход по ссылке.
Цена: сервер не может проверить энтропию токена, но слабый токен вредит только выпустившему.

**Вход по номеру комнаты закрыт.** Операции `join` больше нет: попасть внутрь можно только
погасив приглашение.

**Списание попытки — одним `UPDATE` с условием в самом запросе**, а не «прочитали,
проверили, записали»: второй из двух одновременных переходов обязан получить нулевое число
изменённых строк, а не увидеть ещё не списанный счётчик.

**Ссылка в адресной строке участника больше не содержит ключ комнаты.** После погашения
пишется только `#<номер>`: своя обёртка лежит на сервере, а лишний секрет в истории
браузера и на чужом экране ни к чему. Форма `#<номер>.<ключ>` ещё читается, но не пишется.

**Проверено руками:** выпуск ссылки владельцем, переход по ней с другого устройства
(развернул эфемерным ключом, перешифровал под свой X25519, читает ленту), второй переход
по той же ссылке даёт ровно «приглашение недействительно», перезагрузка гостя без ключа
в ссылке поднимает ленту через обёртку.

### Закрытие регистрации — СДЕЛАНО

Миграция `V2__instance_owner.sql`. Отдельная таблица, а не роль в `member`: до первой
комнаты участия ещё нет, а право заводить комнаты уже нужно. Owner-инвайт — это строка
`invite` с `room_id IS NULL`; схема допускала NULL с самого начала.

**Пропуск на сервер даёт погашенное приглашение**, а не подпись: подпись говорит «это тот же
ключ», а не «его сюда звали». Пропуском считается владение сервером либо участие хотя бы
в одной комнате — «создать комнату может любой участник», как в README.

**Owner-инвайт печатается один раз** и только если нет ни владельца, ни живого owner-инвайта.
Никакого повторного онбординга после рестарта. Это единственное место, где токен делает
сервер: клиента здесь ещё нет. В базу, как везде, ложится только хэш.

**Проверено руками:** без приглашения — «нужно приглашение» и никакой комнаты; переход по
напечатанной ссылке делает владельцем и заводит первую комнату; приглашение оттуда пускает
второе устройство; рестарт ссылку не печатает; в базе один владелец, ноль инвайтов.

**Задачи**
- Генерация: 32 случайных байта из `SecureRandom`, base64url. Плюс **эфемерная пара X25519
  на каждый инвайт**. Ссылка: `https://host/join#<token>.<ephemeral_priv>`.
  Всё после `#` — на сервер не уходит.
- **В ссылке едет не `room_key`, а эфемерный приватный ключ.** Сам `room_key`, обёрнутый под
  эфемерный публичный, лежит на сервере в `invite.wrapped_key` и удаляется вместе с погашением
  инвайта. Иначе пересланная в мессенджер ссылка навсегда остаётся ключом от комнаты, даже
  после того как инвайт исчерпан, — а превью-боты и архивы такие ссылки видят.
- В базу — только `SHA-256(token)`, `role`, `wrapped_key`, `expires_at`, `uses_left`.
- При погашении новичок разворачивает `room_key` эфемерным ключом, тут же перешифровывает его
  под свой X25519 и отдаёт серверу обёртку в `member_key`. Строка `invite` удаляется.
- Погашение атомарно, в одной транзакции: проверка срока и счётчика, декремент,
  создание `member`. Гонка двух одновременных переходов не должна дать лишнего участника.
- Отзыв инвайта владельцем. Каскадный отзыв по `invited_by` — по явной команде, не автоматом.
- Ответ на невалидный, протухший и исчерпанный токен — **один и тот же**.

**Готово когда** одноразовый инвайт при двух параллельных запросах срабатывает ровно раз.

## Фаза 7. Сообщения, TTL, догрузка — СДЕЛАНО

Срок выбирает отправитель кнопкой в композере (5 мин / 1 ч / 24 ч / 48 ч / 5 сут),
**зажимает его сервер** в `[60, room.max_ttl]` — в `MessageService`, там же, где рождается
дедлайн. Молчание отправителя — срок комнаты по умолчанию, а не «навсегда».

Потолок реплики 64 КБ, проверяется до записи.

Кадр несёт `expiresAt` абсолютным: вкладка может простоять в фоне сколько угодно, и
пересчитывать остаток от момента доставки нельзя. Клиент гасит реплику **за последние
десять минут независимо от срока** и убирает её из DOM по дедлайну — сервер её к тому
времени уже не отдаёт.

Sweeper раз в 30 секунд и на старте, чистит `message`, `onetime`, `invite` — включая
**исчерпанные** инвайты: пока строка жива, она держит `wrapped_key`, и сохранённая кем-то
ссылка остаётся заряженной. Место возвращает `PRAGMA incremental_vacuum(256)` порциями.

Удаление файлов вместе с блобами — фаза 8, таблицы `file` пока нет.


**Задачи**
- Отправка: срок жизни выбирает отправитель, сервер **зажимает** его в диапазон
  `[60, room.max_ttl]` и ставит `expires_at = now + clamped`. Значение от клиента без зажима
  не принимать. Пустое значение — `room.default_ttl`. Валидация размера (лимит 64 КБ).
- Чтение истории: `SELECT … WHERE room_id = ? AND id > ? AND expires_at > ? ORDER BY id`.
- Реконнект: клиент хранит `last_seen_id`, после подписи challenge шлёт `since` и добирает пропущенное.
- Sweeper:

```java
@Scheduled(fixedDelay = 30_000)
public void sweep() {
    long now = System.currentTimeMillis();
    jdbc.update("DELETE FROM message WHERE expires_at < ?", now);
    jdbc.update("DELETE FROM invite  WHERE expires_at < ? OR uses_left <= 0", now);
    jdbc.update("DELETE FROM onetime WHERE expires_at < ?", now);
}
```

  Тот же метод — на `ApplicationReadyEvent`.
- Возврат места: `PRAGMA incremental_vacuum` небольшими порциями после уборки. Полный `VACUUM`
  не использовать — он блокирует базу целиком и требует вдвое больше места на диске.
- **Sweeper не удаляет файлы напрямую.** Для `file` порядок обратный: выбрать протухшие,
  удалить блоб с диска, затем строку. Одним `DELETE`, как остальные таблицы, нельзя —
  потеряется путь к блобу и он останется на диске навсегда.

**Готово когда** после суток простоя сервер стартует, чистит базу до раздачи трафика,
а клиенты добирают ровно непрочитанное.

## Фаза 8. Передача файлов — СДЕЛАНО

Миграция называется `V3__files.sql`: номер 2 уже занят закрытием регистрации.

**Лимит проверяется трижды, и только две проверки чего-то стоят.** В браузере — 20 МБ
открытого текста, это чистое UX. На сервере — `Content-Length` до чтения тела и фактически
прочитанные байты во время. Первую серверную обойти легко: заголовок пишет клиент, а при
chunked-кодировании его нет вовсе, — поэтому решает вторая, с обрывом чтения на пороге
и удалением недописанного куска.

Порог задан **в байтах шифротекста** (21 МБ), не открытого текста: 20 МБ через
`secretstream` дают 20 972 904 байта, и порог по открытому тексту давал бы ложные отказы
на файлах у самой границы.

**Undertow режет тело на 2 МБ раньше нашей проверки.** Это его умолчание, и снаружи оно
выглядит как обрыв связи без причины: приложение до своего отказа не доходит. Поднято
в `application.yml` до `max-http-post-size: 22085632` — с запасом над нашим потолком,
чтобы отбивал перебор наш код, отвечая 413. Два числа менять только вместе.

**Пропуск на загрузку выдаётся по сокету и едет заголовком**, а не параметром запроса:
параметры попадают в `access.log` веб-сервера, и одноразовость токена этого не отменяет.
Место резервируется в момент выдачи — иначе пачка одновременных запросов проходит квоту
хором, потому что в базе на тот момент пусто у всех.

**Скачивание открыто без входа**: адрес блоба и есть пропуск к нему. Внутри шифротекст
под случайным ключом файла, а ключ живёт в сообщении комнаты, поэтому угадавший имя
получает мусор. Это же нужно фазе 9: одноразовая ссылка отдаёт файл, не выдавая ключ комнаты.

**Признак «загрузка ещё идёт» — невыданный токен, а не возраст файла.** Сначала скан
осиротевших сравнивал время на диске с часами приложения; на подставных часах в тестах
это разъезжается, а в бою разъедется на любом сдвиге времени. Теперь в памяти лежит набор
выданных, но не завершённых загрузок, и скан их пропускает.

Скан осиротевших — только на старте, не каждые полминуты: сирота появляется от падения
между записью тела и вставкой строки либо от удаления комнаты (каскад в схеме сносит строки,
но про файловую систему не знает), оба случая редкие, а обход каталога дорожает с числом файлов.

**Формат сообщения теперь конверт с версией** — `{v, t, …}`, текст и файл различаются полем
`t`. Поле версии обязано быть с самого начала: без него смена криптосхемы ломает всё
отправленное, и миграцию некуда зацепить.

Проверено вручную на двух личностях (`localhost` и `127.0.0.1` — разные origin, разные
IndexedDB): файл в 300 КБ уходит, второе устройство скачивает и расшифровывает его байт
в байт, в журнале сервера не появляется ни токена, ни имени блоба. Удаление строки из базы
с последующим рестартом убирает осиротевший блоб.

**Задачи**

- Миграция `V3__files.sql`:

```sql
CREATE TABLE file (
  id            TEXT PRIMARY KEY,      -- случайный, не производный от имени
  room_id       TEXT NOT NULL REFERENCES room(id) ON DELETE CASCADE,
  uploader      TEXT NOT NULL,
  size_bytes    INTEGER NOT NULL,      -- размер шифротекста
  created_at    INTEGER NOT NULL,
  expires_at    INTEGER NOT NULL
);
CREATE INDEX idx_file_expires ON file(expires_at);
```

  Ни имени файла, ни MIME-типа, ни ключа в схеме нет — сознательно.

- Блобы на файловой системе, `data/blobs/<id>`, не в SQLite. При TTL-удалении файловая
  система освобождает место сразу, база не пухнет и не требует долгого `VACUUM`.
  Бэкап теперь покрывает весь каталог `data/`, а не только `messenger.db`.

- Загрузка отдельным HTTP-эндпоинтом, не по WebSocket: `POST /api/file` с телом
  `application/octet-stream` (без multipart — парсить нечего, тело уже шифротекст).
  Авторизация — короткоживущий upload-токен, который клиент запрашивает по сокету.

- **Лимит проверять на сервере дважды**: по `Content-Length` до чтения и по фактически
  прочитанным байтам во время чтения, с обрывом соединения при превышении. Клиентская
  проверка — только UX. Порог задавать в байтах шифротекста (~21 МБ), не открытого текста,
  иначе получите ложные отказы на файлах ровно по границе.

- Шифрование на клиенте: `crypto_secretstream_xchacha20poly1305`, чанки по 256 КБ,
  **случайный ключ на каждый файл**. Ключ, имя и MIME-тип кладутся внутрь сообщения,
  которое и так зашифровано `room_key`.

  Что это даёт: файл переживает ротацию эпох, его можно отдать одноразовой ссылкой
  без выдачи ключа комнаты, а удаление сообщения обесценивает блоб, даже если тот ещё лежит.

- Скачивание: `GET /api/file/{id}` отдаёт шифротекст, клиент расшифровывает в памяти
  и подставляет blob-URL. На 20 МБ это работает без Service Worker.

- Квота на комнату и общая квота на диск. При исчерпании — внятный отказ, не 500-я.

**Порядок удаления — сначала блоб, потом строка в БД.** Обратный порядок оставляет на диске
вечный мусор, о котором никто не знает. При старте — скан `data/blobs/` на осиротевшие файлы.

**Готово когда** файл в 21 МБ отбивается сервером даже при подделанном `Content-Length`,
а после TTL исчезают и строка, и блоб.

## Фаза 9. Одноразовые ссылки — СДЕЛАНО

`DELETE … RETURNING` через xerial работает: восемь одновременных открытий дают ровно одного
победителя. Проверять это стоило до всего остального — на неудаче пришлось бы городить
транзакцию с `SELECT` и `DELETE`.

**Страница `/once` отдельная от SPA, а не маршрут внутри неё.** Открывающий может быть
посторонним, а SPA при загрузке заводит личность устройства и лезет в сокет — постороннему
всё это незачем. Отдельная страница просит только libsodium, ключ берёт из фрагмента и
уходит на сервер ровно по нажатию.

**Токен едет телом POST, а не в пути.** Путь попадает в `access.log` веб-сервера, и
одноразовость этого не отменяет: журнал переживёт саму записку. GET и HEAD по ссылке
ничего не тратят — проверено curl'ом с юзерагентом превью-бота.

После открытия фрагмент убирается из адреса: перезагрузка уже ничего не откроет, а ключ
в истории браузера и на чужом экране ни к чему.

Ключ у записки свой, не ключ комнаты: ссылку отдают наружу, и ключом комнаты она открывала бы
всю переписку. Привязка к комнате в схеме всё равно нужна — иначе удаление комнаты записки
не заденет.

**Попутно нашёлся баг не из этой фазы.** Погашение owner-инвайта роняло сессию:
`announceRoster` шёл в реестр с `room_id = null`, а там ключ карты. Наружу это выглядело
исправной работой, потому что вкладка молча переподключалась. Закрыто тестом
`survivesRedeemingAnOwnerInviteOnTheSameSession`.

**Задачи**
- Шифротекст на сервере, ключ во фрагменте.
- Выдача атомарна, SQLite однопоточен на запись — гонка исключена:

```sql
DELETE FROM onetime WHERE token_hash = ? AND expires_at > ? RETURNING ciphertext;
```

- Открытие **не по GET**: промежуточная страница с явным подтверждением, сжигание по POST.
  Иначе превьюшки мессенджеров и корпоративные антивирусы сожгут ссылку до человека.
- Пустой результат — тот же ответ, что и для несуществующего токена.

**Готово когда** пересылка ссылки в мессенджер с превью не сжигает её.

## Фаза 10. Личные сообщения — СДЕЛАНО

Миграция называется `V4__direct.sql`: третий номер занят файлами.

**Ключ переписки лежит в своей таблице `dm_key`, а не колонкой в `member_key`.** Там
`wrapped_room_key` объявлен `NOT NULL`, а кладёт эту обёртку другой участник — свой же ключ
переписки человек публикует сам, и порядок двух событий не задан. Колонка потребовала бы
вставлять строку с выдуманной обёрткой.

**Ключ переписки выводится из seed, а не хранится.** `BLAKE2b(seed, "dm:<комната>:<эпоха>")`.
Случайный пришлось бы держать отдельно, и восстановление из 24 слов вернуло бы комнаты,
но не собственную личную переписку.

**Настоящих конвертов два: получателю и себе.** Иначе отправитель не читает собственную
переписку — своего слота у него нет. Снаружи два настоящих неотличимы от нуля настоящих:
для того, у кого нет ключа, это случайные байты.

**Подпись внутри шифротекста — не формальность.** Ключ сообщения выбирает сам отправитель,
поэтому поле «от кого» без подписи не стоит ничего: любой участник назвался бы чужой картой.
Подписывается `комната \n эпоха \n карта получателя \n текст` — без комнаты и эпохи подпись
переносится в другую комнату и переживает ротацию.

**Найдено живой проверкой на двух устройствах:** после публикации ключа переписки сервер
не рассылал состав заново, и вторая сторона узнавала о ключе только при следующем входе —
до тех пор написать было нечем. Теперь `dm-key` тянет за собой `announceRoster`.

Проверено на двух личностях (`localhost` и `127.0.0.1`): переписка идёт в обе стороны, карты
подставляются верно, в общей ленте личного нет, кнопка вложения в нити выключена. На реальных
строках из базы: у получателя открывается ровно один слот из 52 — свой, — у постороннего
ключа ни одного, все слоты по 80 байт, нулевых нет.

Не проверено: третий участник живьём. Третий origin пришлось бы брать по IPv6 (`[::1]`),
а панель браузера не поднимает туда WebSocket — HTTP по тому же адресу работает. Что
посторонний не отличит конверт, проверено ключом постороннего на настоящих строках.

**Не сделано из задач фазы:** личное сообщение не считается ни в какую квоту. Квоты на
сообщения в базе нет вообще — ни у обычных, ни у записок, — и заводить её отдельно для
личных значило бы прикрыть один путь из трёх. Место для этого фаза 11.

Личная переписка живёт внутри комнаты: карта существует только здесь, отдельного списка
контактов быть не может — он связал бы личности между комнатами.

**Получатель скрыт от сервера.** Сообщение адресуется не конкретному ключу, а всей колоде:

1. Случайный ключ `K`, текст шифруется им один раз.
2. 52 конверта по числу мест. В слоте получателя — `crypto_box_seal(K, pubkey_dm)`.
   В остальных 51 — **случайные байты той же длины**. Вывод sealed box неотличим от случайного
   для того, у кого нет ключа, поэтому сервер не видит, какой конверт настоящий.
3. Клиент пробует развернуть только свой слот, по номеру своей карты. Одна попытка, не 52.

Шифровать целиком под каждого не нужно: конверт несёт 32 байта ключа, а не текст. Накладные
расходы — около 4 КБ на сообщение независимо от его длины.

**Задачи**

- Миграция `V3__direct.sql`:

```sql
CREATE TABLE direct (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  room_id     TEXT NOT NULL REFERENCES room(id) ON DELETE CASCADE,
  ciphertext  BLOB NOT NULL,   -- текст под K
  envelopes   BLOB NOT NULL,   -- 52 слота фиксированной длины, порядок = номер карты
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER NOT NULL
);
CREATE INDEX idx_direct_room    ON direct(room_id, id);
CREATE INDEX idx_direct_expires ON direct(expires_at);
```

  Поля получателя нет и быть не должно. Ни отправителя: он подписывается **внутри**
  шифротекста, иначе подпись выдаст пару снаружи.

- Слоты фиксированной длины и всегда все 52, включая места выбывших. Переменная длина или
  пропуски сразу выдают, какой конверт настоящий.

- `pubkey_dm` — отдельный ключ переписки, свой на каждую эпоху комнаты. Добавляется в
  `member_key`. Без этого утечка долгоживущего ключа раскрывает всю личную переписку задним
  числом: ротации ключа комнаты она не подчиняется.

- Сроки — те же правила и тот же зажим на сервере: по умолчанию 48 часов, потолок 5 суток.
  Отдельного потолка для личных сообщений не вводить.

- Sweeper чистит `direct` наравне с `message`.

- Квота: личное сообщение весит примерно на 4 КБ больше обычного. Считать в общую квоту комнаты.

- Настройка комнаты «личные сообщения запрещены», решается при создании. Администратор не
  может модерировать то, чего не видит, и в некоторых комнатах это неприемлемо.

**Интерфейс** — отдельная вкладка, не врезка в общую ленту. Внутри список нитей по картам.
В общей ленте личных сообщений нет вовсе, чтобы не путать личное с общим.

**Известная утечка, принята сознательно.** Вложение в личном сообщении разослать всем нельзя:
блоб один, и сервер видит, кто его скачивает. То есть текст получателя скрывает, а файл выдаёт.
До появления решения — **файлы в личных сообщениях не поддерживаются**, а не «поддерживаются
с оговоркой».

**Готово когда** сервер по содержимому `direct` не может определить получателя, а посторонний
участник не отличает настоящий конверт от случайного.

## Фаза 11. Модерация и анти-абьюз — СДЕЛАНО

**Исключение: сначала пометка в базе, потом ротация эпохи, потом разрыв сессий.** Закрыть
сокет первым значит дать секунду на переподключение, пока членство ещё числится за
человеком. Ротация не косметика: без неё исключение — запись в базе, а ключ комнаты у
человека остался. Обёртки новой эпохи ему уже не выпишут, он выпал из `membersWithoutWrapper`.
Карта остаётся занятой навсегда, `seats_taken` не уменьшается.

**Порог proof-of-work в ноль битов выключает проверку.** Это настройка для закрытого
сервера, где комнаты заводит десяток знакомых людей, и она же позволила оставить тесты
протокола без пропусков — иначе каждый из них решал бы задачу впустую.

Соль выдаёт сервер и гасит при предъявлении, гашение до проверки решения: заготовить
решение заранее нельзя, использовать дважды тоже. На 18 битах браузер тратит 60–450 мс —
измерено, пять прогонов. Перебор синхронный и вкладку подвешивает, поэтому в статусе
на это время появляется «считаю пропуск…».

**Счётчик записи один на все виды.** Отдельные счётчики для ленты, записок и личных
означали бы, что спам просто перетекает из одного в другое.

Окно у лимитера фиксированное, а не скользящее: скользящее требует держать историю попыток
по каждому ключу — то есть ровно ту память, которую лимитер и должен беречь. Уборка
срабатывает не по расписанию, а когда ключей стало много.

**Зачистка стирает содержимое, а не комнату.** Участники, карты и обёртки остаются, разговор
продолжается с чистого листа. Вложения уходят первыми: у них есть вторая половина на диске.

Проверено руками: пропуск считается и на создание комнаты, и на выпуск приглашения;
исключение поднимает эпоху с 1 до 2, рвёт сессию исключённого, а после его переподключения
сервер отвечает «нет доступа к комнате»; карта исключённого остаётся занятой; зачистка
опустошает `message`, `direct`, `onetime` и `file`, оставляя саму комнату.

**Не покрыто тестом:** потолок на адрес. Отличить его срабатывание от потолка на устройство
внутри одного процесса нечем — исходный адрес у всех соединений один. Сам счётчик проверен
как счётчик, проводка до адреса — нет.

**Задачи**
- Удаление участника: снятие из `member`, инкремент эпохи, перевыпуск обёрток, разрыв
  его живых сессий в `SessionRegistry`.
- Rate limit по IP и по устройству: создание комнат, выпуск инвайтов, отправка сообщений.
  Счётчики в памяти, на диск не писать.
- Proof-of-work (hashcash) на создание комнаты и выпуск инвайта вместо капчи.
- Ручной wipe комнаты владельцем — немедленное удаление всех сообщений.

## Фаза 12. Упаковка и эксплуатация — СДЕЛАНО

Файлы развёртывания лежат в `deploy/`, а не в README врезками: то, что набирают руками
с экрана, расходится с реальностью на второй правке.

**Сборка воспроизводима** — `preserveFileTimestamps = false` и `reproducibleFileOrder = true`
в `bootJar`. Проверено: два прогона через `clean` дают побайтно одинаковый jar. Без этого
опубликованный хэш подтверждает только, что файл не побился при скачивании, а собрать тот же
артефакт из тех же исходников и сверить самому нельзя.

**Хэшей два, и отвечают они на разные вопросы.** Сумма jar (`./gradlew releaseHashes`) — тот
ли файл скачали. Отпечаток бандла — тот ли код сервер раздаёт браузерам прямо сейчас; он
считается по всему, что уходит в браузер, и печатается при каждом старте. По jar его считать
нельзя: там ещё классы, зависимости и миграции, и его сумма меняется от вещей, к раздаваемому
коду отношения не имеющих.

Отпечаток печатается в журнал, а не отдаётся эндпоинтом: админ читает свой journald, а лишняя
ручка наружу сообщала бы точную версию всякому, кто спросит.

**Журнал Caddy настроен вырезать query-строку целиком и обрезать адрес до подсети.** Секретов
в query нет по устройству системы, но вызов входа, ключ устройства и подпись там есть, а
полный адрес в файле на диске — это уже история соединений конкретного человека.

**Не проверено:** Dockerfile, compose и Caddyfile написаны, но не запускались — на машине
стоит клиент docker без демона, а поднимать его тут незачем. Проверяются командами
`docker build -t anteroom .`, `docker compose up -d --build` и
`caddy validate --config deploy/Caddyfile`. `docker compose config` разбирается, синтаксис
`backup.sh` проверен `sh -n`.

**Не сделано:** GraalVM native-image. В плане он помечен опциональным, требует отдельного
тулчейна и сам по себе меняет поведение (рефлексия, ресурсы, криптопровайдеры) — то есть
это не упаковка, а отдельная работа с собственным риском.

**Задачи**
- Основной способ развёртывания — **systemd-юнит**: `java -jar` с `--app.data-dir`, `Restart=on-failure`,
  запуск от отдельного пользователя, логи в journald. Это ближе всего к обещанию «скачал и запустил».
- Caddy отдельным процессом впереди: автоматический TLS, `access.log` без query-строк.
- Docker и compose — **опция**, не основной путь. Полезны тем, у кого уже есть окружение с
  контейнерами. Не делать их единственным документированным способом: контейнер прячет каталог
  `data/` за томом, и история с бэкапом перестаёт быть очевидной.
- Бэкап: `sqlite3 messenger.db ".backup"` по расписанию плюс копия `data/blobs/`. Простой `cp`
  живой базы не годится, `.backup` на WAL — да.
- Опционально GraalVM native-image: ~60 МБ и мгновенный старт вместо 150–250 МБ.
- Релизы подписываются, хэш бандла публикуется.

## Фаза 13. Приёмочный прогон по безопасности

Отдельный чеклист, прогоняется перед каждым релизом:

- [ ] Grep по логам за сутки работы: нет токенов, ключей, фрагментов URL, шифротекстов.
- [ ] Дамп базы: нет открытого текста, нет сырых токенов, только хэши.
- [ ] Удалённый участник не получает сообщений новой эпохи.
- [ ] Протухшее сообщение недоступно и в окне между тиками sweeper'а.
- [ ] Повторный и протухший одноразовый токен неразличимы в ответе.
- [ ] Replay challenge отбивается.
- [ ] Имя файла и MIME-тип отсутствуют в БД и в логах.
- [ ] Срок жизни больше `max_ttl`, присланный клиентом, зажимается сервером.
- [ ] Выбывшая карта не выдаётся новому участнику; 53-й вход отклоняется как конец колоды.
- [ ] После TTL не осталось ни строки в `file`, ни блоба в `data/blobs/`.
- [ ] Исчерпание квоты даёт внятный отказ, а не 500-ю.
- [ ] Погашенный инвайт больше не даёт `room_key`: старая ссылка бесполезна.
- [ ] В `direct` нет ни поля получателя, ни признака, по которому его можно вычислить:
      все 52 слота одной длины, настоящий неотличим от случайного.
- [ ] Рестарт: комнаты и участники на месте, повторный онбординг не запрашивается,
      owner-инвайт в stdout не печатается.

## Что осознанно не делаем

- **Double Ratchet** — избыточен для десятков людей, ротации эпох достаточно.
- **Групповые звонки и файлы свыше 20 МБ** — отдельная задача, не в первом релизе.
- **Сокрытие метаданных** — сервер видит, кто когда с кем и с каким сроком жизни. При self-host
  сервер свой, и это приемлемо. Sealed sender — кандидат на будущее (паддинг перенесён в работу,
  см. TODO в CLAUDE.md).
- **Гарантия удаления у собеседника** — недостижима. Написать это прямо в UI, а не делать вид.
